# Sidebar and tabs

betterlink keeps a live mirror of every open tab in your Chromium browsers, in true realtime, both ways, and shows it in the sidebar beside the browser window. Open, close, move or switch a tab in the browser and the sidebar changes in the same instant (a title or icon that keeps changing shows at most 10 times a second while a browser is in front and every 2 seconds while another app is, see docs/resources.md); open, focus or close a tab from the sidebar and the browser does it immediately. No polling anywhere. The Sidebar page holds the sidebar's settings and browser setup; it doesn't list tabs itself.

The extension runs a short list of tab commands: open, focus, close (one or several), move, mute, duplicate, reload, send to an address, and move to a new window.

## How it works

```
 Browser (Chrome, Dia, Brave, Arc, Edge…)
   browser-extension/background.js  ── chrome.tabs / chrome.windows events, pushed as they fire
        │  native messaging: stdio, 4-byte length + JSON   (connectNative keeps the worker alive)
        ▼
 betterlink-tabhost  (Contents/Helpers; one process per browser, launched by the browser)
        │  Unix socket, newline-delimited JSON
        │  ~/Library/Application Support/betterlink-tabs/sockets/<browser>-<pid>.sock
        ▼
 betterlink (sidebar)   ── SyncHub: watches the socket folder with kqueue, one TabStore per browser
```

- **Browser to app.** The extension subscribes to every tab and window event (`onCreated`, `onRemoved`, `onUpdated`, `onMoved`, `onActivated`, `onAttached`, `onDetached`, `onReplaced`, window create/remove/focus) and forwards each one the moment Chrome fires it, stamped with a sequence number and the browser's clock. The window events are asked for the window types the snapshot lists (normal, popup and app, `WINDOW_TYPES`): left to itself Chrome sends them only for normal and popup windows, so an app window would open unannounced (0.3.3). A window's removal is asked for every type, so a window sent because a tab named it (DevTools, below) is reported gone too.
- **App to browser.** The app writes a command to the socket (`open`, `close`, `closeMany`, `activate`, `move`, `mute`, `duplicate`, `reload`, `navigate`, `newWindow`, `snapshot`; `Command.Op` in `Messages.swift`, and a test keeps that list equal to the extension's `OPS`); the host frames it onto the browser's stdin; the extension runs the real `chrome.tabs` call and acks. The ack of an `open` or a `duplicate` names the tab it made. The resulting change comes back through the normal event path, so the app has one source of truth.
- **Old and new copies work together.** The extension's hello lists the commands it runs (`ops`, since 0.2.0). The sidebar offers an action only when the connected copy can do it (`BrowserSession.can`), so an unpacked copy that hasn't been reloaded keeps working with what it has: open, close, focus. Each window comes with the browser's own word for what it is (`windowType`: normal, popup or app, since 0.3.2); a window from an older copy comes with none and counts as normal. A tab that names a window the app was never sent (one of a type that has no events here, such as DevTools) makes the extension ask what that window is and send it right behind the tab (0.3.3), so the app doesn't take it for a normal one.
- **Either side can start first.** Each host listens on its own socket; the app watches the folder with kqueue (inotify on Linux) and connects the instant a socket appears. On connect the host asks the extension for a full snapshot. When the browser quits, the host sees EOF, removes its socket and the app drops that browser. A crashed host's leftover socket is removed by the app.
- **Self-healing.** `TabStore` is a pure reducer over the event stream. A gap in sequence numbers makes it ask for a fresh snapshot. Events and acks that come while the extension is reading a snapshot wait and go out right behind it, numbered after it (0.3.4), so none can be numbered before a snapshot that misses it; when one of them put a tab at an index, the snapshot is read again instead (at most three readings), since replaying it over a list that already shows it could leave the order wrong. As a browser comes to the front, the app also checks each of its lists with a snapshot that leaves out the icons (`Command.refresh`), at most once a minute per connection and never in the first minute after it connected (`RefreshPacer`); the store keeps each tab's icon while its address is the same.
- **Connecting quickly.** When no host answers, the extension tries again after 1 s, doubling to 60 s. A tab or window event while it has no host tries at once, at most every 3 s (`reconnect.js`, 0.3.4), so after Set Up, or when betterlink starts after the browser, the sidebar fills on the next click in the browser instead of after up to a minute. With no host and no events the browser puts the extension's worker to sleep after about half a minute, and its timers stop with it; the next tab or window event wakes it, and waking connects at once.
- **What is connected.** The Sidebar page's row for each browser says which of its profiles have the extension connected and on what version, and which run an older copy than betterlink's (`ExtensionConnections`). `betterlink tabs helpers` gives the same, per browser, as `extension` and `profiles`.
- **Multiple browsers at once.** Each browser (and each profile) runs its own host, so the app follows Chrome and Brave at once, and every window of each has its own sidebar. The host names itself after the app that launched it.

Nothing polls. The timers are the extension's reconnect backoff (1s doubling to 60s) for when the host is not installed, and the app's pacing of titles and icons (docs/resources.md). The check as a browser comes to the front runs on that event, not on a timer.

## Measured

`make test-tabs` runs the real extension bridge (against a simulated `chrome.tabs`), the real `betterlink-tabhost` binary and the real app-side `SyncHub`:

```
browser->app: 1.0 ms; app->browser->app: 1.7 ms; host-measured event latency: 0.34 ms
```

The terminal view (`betterlink-tabs`) prints the event latency (browser fired it → app applied it) for every event; with `--json` it also reports the command round trip.

## Try it

1. Build and run betterlink (CONTRIBUTING.md: use a `BETTERLINK_HOME` temp folder).
2. Sidebar page › Sidebar › **Show the sidebar**, on. The rest of the page (Browsers, the sidebar's side and shortcut, Options, Import) shows only while it is on.
3. Sidebar page › Browsers › **Set Up** next to the browser. That writes one file, `NativeMessagingHosts/com.wkoutre.betterlink.tabs.json`, in that browser's data folder, pointing at this betterlink's `Contents/Helpers/betterlink-tabhost`. **Uninstall** deletes it.

   Brave is the exception: on macOS it reads Google Chrome's folder (`Google/Chrome/NativeMessagingHosts`) and never its own (verified on Brave 1.100 with its default and a custom data folder, 2026-11-27). So Set Up for Brave writes the file into both folders, and the Sidebar row checks the one in Chrome's folder (and that Brave's own is there, so Uninstall in Brave reads as done). Since the file is shared, Set Up in one also shows the other as set up. Chrome and Brave then share that file: Uninstall in one leaves it while the other is set up (for Chrome, while Brave's own file is there; for Brave, while Chrome has ever run on this Mac) and says so. A Brave set up by an older betterlink, with only its own file, gets the shared one when the Sidebar page or the sidebar first starts.
4. In that browser: chrome://extensions › Developer mode › Load unpacked › `browser-extension/` (the repository's folder while you are changing the extension; see below for an installed betterlink).

## The extension on a Mac without the repository

The extension is not in the Chrome Web Store yet (docs/tabs-store.md), so it is loaded unpacked. It ships inside betterlink.app (`Contents/Resources/browser-extension`, put there by `make build`), and betterlink keeps a copy in one folder that is the same on every Mac:

```
~/Library/Application Support/betterlink-tabs/extension
```

Once per browser profile:

1. Sidebar page › Browsers › **Show in Finder**, with **Show the sidebar** on (or `betterlink tabs extension`, which prints the folder).
2. In the browser, open chrome://extensions and turn on Developer mode.
3. Drag the `extension` folder from Finder onto that page. (Load unpacked works too: press ⌘⇧G in its file picker and paste the path, because `~/Library` is hidden.)

Leave Developer mode on: the browser turns an unpacked extension off without it. No browser lets an app do these steps for you on a Mac it doesn't manage.

After that the extension follows the app (`ExtensionCopy`, unit tested):

- When betterlink starts the Sidebar page or the sidebar, it replaces the folder's files if its own copy is newer. It never downgrades the folder (two betterlinks on one Mac keep the newer extension), and it only writes into an empty folder or an earlier copy of this extension.
- The browser reads the folder again each time it starts. A browser that is already running is told to reload the extension (`reloadSelf`, extension 0.3.0), once per connection. The extension reloads only if the manifest on disk has another version than the one running, so a copy loaded from another folder, or the store's copy, stays as it is and nothing can loop.
- Bump `version` in `browser-extension/manifest.json` with every change to the extension: that is what both sides compare.

Under `BETTERLINK_HOME` the folder is `tabs-extension` inside it, so a test or development run never replaces the extension a browser is really using. `BETTERLINK_TABS_EXTENSION_DIR` puts it anywhere.

The extension's id is its Chrome Web Store item id, `gjjllnebeeegbipppiclhlomdppbnljh`. The `key` in its manifest is that item's public key (checked by a test), so an unpacked copy has the same id and `allowed_origins` matches both. A registration written for another id shows as "Points elsewhere": press Set Up Again. Nothing starts until the Sidebar page is opened or the sidebar is turned on.

Tests: `make test` covers TabSyncCore; `make test-tabs` runs the extension bridge tests and the full-pipe e2e.

## The sidebar

Sidebar page › Sidebar › **Show the sidebar** puts a panel flush against the left or right edge of every browser window (a window with tabs, see Which windows below) of every attached browser, the window's full height. Each shows its own window's tabs, under the Sidebar Profile linked to that window's Browser Profile, and follows its window as it moves and resizes. It sits directly above its window among the other windows, so whatever covers the window covers its sidebar, and switching apps changes nothing. A window that is minimized or in native full screen, or whose browser is hidden, has no sidebar until it is back; a window on another Space keeps its sidebar there. On quit, betterlink gives the space it took back to every window it narrowed, all of them together (`AXWindow.placeNow`), each sent the frame it gets whole (see Motion), so quitting waits at most 2.4 s (4 x 0.6 s) however many windows there are and whatever their browsers do: each call may wait 0.2 s for its browser (its Accessibility messaging timeout, lowered for these calls), none is sent that could end past 2.4 s, and a browser that misses one (hung) is sent nothing more for any of its windows. What hasn't landed then is left as it is, the person's, and such a window keeps its record. Turning the sidebar off does the same, and lets each window go after: a window whose browser missed a call is sent nothing then either, so the whole of it stays within 2.4 s.

- **Which windows** (`WindowKinds`, unit tested): a sidebar goes beside a browser window, one with tabs, and beside nothing else of the browser's: not an extension's palette or any other popup, not an app window, not DevTools on its own. What a window is is read from the window, never from its title, and no browser is named. To Accessibility all of these are the same standard window with close, minimize, zoom and full screen buttons, so each is walked once (its own chrome, pages skipped, as the tab takeover does) for a group of tabs, an AXTabGroup holding AXTabButtons. Read live on 2026-11-25:

  | Window | Tab groups | Toolbars with an address field | Sidebar |
  |---|---|---|---|
  | Chrome for Testing 158, Brave 158: a normal window, tabs across the top, in a column, or the column collapsed | 1 | 1 | yes |
  | A popup (`window.open` with `popup`, an extension's palette) | 0 | 1 | no |
  | An app window (`--app=URL`) | 0 | 0 | no |
  | DevTools on its own | 0 | 0 | no |
  | Dia's own browser window (about 82 elements) | 0 | 0 | yes |
  | Picture in picture; Arc, Edge, Vivaldi | not read | not read | |

  Dia shows no tab group in any window, so having one can't be asked of every browser. The rule holds in a browser one of whose windows has been seen with tabs since betterlink began watching it: there only a window seen with tabs gets a sidebar, and one seen with them once stays a browser window (full screen and the tab takeover change what can be seen). A browser never seen with tabs keeps a sidebar on every standard window, as before. All of a browser's windows found together are read before any is judged, so the order they come in decides nothing.

  A window still opening may have no tabs yet. It is looked at again 0.1, 0.3, 0.7, 1.5 and 3 s after it was first seen (one-shot timers; none runs once every window is known), and gets its sidebar at the first look that finds tabs: a sidebar is never shown and then taken away for a window that is only waiting. Live on 2026-11-25, Chrome for Testing 158 and Brave 158 showed a new normal window's tabs at the first look, so the later looks are for a browser that is slower. After the last look the window is taken not to be a browser window, and it keeps that: it is not read again for being listed or focused, so a palette left open costs nothing while you switch between windows. Only an event that can change what that very window shows gives it its looks afresh: it is resized (leaving full screen is a resize) or comes back from the Dock. The same event forgets the browser's word that it is a popup or an app window (`WindowKinds.startOver`): that word came from a pairing, and a window without a sidebar is paired no more, so one wrong pairing would otherwise hold until the window closes.

  One case does take a sidebar away: a window that got one while its browser had not yet been seen with tabs (the browser started with only an app window or a popup readable, a normal window seen later). It gets the same looks, and if none finds tabs its sidebar goes on the next settled pass (0.3 s after the event), never in the middle of an event, and the window gets its space back.

  The browser's own word (`WindowKinds.said`, `WindowWord`, unit tested): what the extension calls the browser window a window is paired with. Paired with one it calls normal, a window is a browser window whatever it shows; paired with a popup or an app window, it is not, and gets no sidebar. In a browser whose windows show no tab group that word is all there is to tell a palette by, so it only helps where the Tabs extension is installed in that browser and profile and connected. Without it nothing can tell, and every standard window of such a browser has a sidebar, a palette included, as before. Tabs seen in the window itself outweigh a pairing that says popup (the pairing is worked out, the tabs are seen). And tabs are trusted only while they agree with the browser: a native tab view reads as a group of tabs too, so once a window the extension calls normal has had its looks and shown none, tabs decide nothing more in that browser and no window loses its sidebar for want of them.

  Where tabs can't tell and the extension is connected, a new window is followed for its title and place but gets no sidebar until its word comes (the pairing needs both, so it is paired like any window; `BrowserWatcher`, `TrackedWindow.awaitsWord`), for at most 0.6 s (`WindowKinds.wordWait`): then it gets one as before, and loses it on the settled pass if a later word says popup. A palette is opened many times a day and must not flash a sidebar, and a real window's sidebar coming a moment later costs less. So in such a browser a window the extension doesn't report (an Incognito window without Allow in Incognito, a profile without the extension) gets its sidebar 0.6 s late. The 0.6 s is twice the 0.3 s the pairing gives the focus to hold, and not yet measured against a real browser: `BETTERLINK_TRACE=1` logs `kinds: … appeared`, `ext: … listed as …`, `pair: …`, and `kinds: … waited N ms for its word: normal`, `not normal` or `none came`, and for each look the calls and milliseconds it took. Where tabs do tell (Chrome, Brave) nothing waits: a window seen with tabs gets its sidebar at that look.

  Not run: Dia itself. Nothing is installed in or attached to the owner's Dia on this Mac, and the one reading of it was taken without touching it. What is said of Dia here follows from that reading (no tab group) and from the rules above, which are unit tested; that a palette in Dia pairs with its popup (the pairing goes by title and place) and how long that takes are still to be seen there.

  The walk is the tab takeover's (`ChromeWalk`): both read a window's chrome through the one walk, so they can't come to see different windows.
- **Tracking** (`Sidebar/WindowTracker.swift`, `BrowserWatcher.swift`) is event-driven: NSWorkspace says which apps launch, quit and come to the front, and when another Space shows; one `AXObserver` per running attached browser reports its windows coming and going, focused, moved, resized, minimized and renamed. During a live drag of the window in front the frame comes from the window server, not the browser: on every mouse-drag event (a global mouse monitor, which needs no permission) and once per display refresh until mouse up. A window is "settled" 150 ms after its last move with the mouse up; only then is it narrowed to make room. Needs the Accessibility permission; the page asks for it. Accessibility lists only the windows on a Space that is showing, so a window on a Space not shown since betterlink started gets its sidebar when that Space shows. A window is told from its browser's others by its window-server number, which Accessibility gives only through `_AXUIElementGetWindow` (not public API): two windows of one browser often share a frame. Should macOS drop it, windows get no sidebar, and the Sidebar page and `betterlink sidebar settings get` (`canTellWindowsApart`) say so. No call to a browser waits longer than a second for its answer, and a browser that doesn't answer is not asked again on Space and display changes until it sends an event.
- **Among the windows** (`SidebarPresence`, unit tested): each panel is an ordinary window ordered next to its browser window by that window's number, and lives on its window's Space. Whether it is where it belongs is read from the window list on the events that can change it (an app coming forward, a window focused, minimized or hidden, another Space showing, a click in the panel, the extension reporting one window more or fewer) and once more 0.3 s later, when windows and Spaces have stopped moving; never on a timer. A window that closes loses its sidebar whatever has the focus: when Accessibility says it is gone, or when the window server no longer lists it (`WindowPairing.closed`, unit tested; read on the events that count the windows), which is the moment the extension says a window went if the browser is late with the first. Should the browser still hold the window then, its sidebar leaves the screen all the same, 0.3 s later, for its window is no longer on it. Whichever says it first, the window is let go once (`BrowserWatcher.remove`): its sidebar, or its wait for the browser's word if it had no sidebar yet, and what was known of what kind of window it is. A window that was judged not to be a browser window and never followed says nothing when it closes: what was known of it is forgotten when the window server's list is next read without it. What the extension reports includes its popups and app windows, so a palette opening or closing has the windows counted again. Above or below the window is decided in one place (`SidebarPresence.relation`): above. Under its window the panel takes the window's shadow (measured: the sidebar 15 to 32 percent darker along the seam), and the pair would no longer read as one window. A window moved to another Space takes its sidebar along when it is next seen there.
- **Which browsers** (Sidebar page › Browsers): every installed Chromium browser by default. Safari isn't offered until its extension ships. Each window of each attached browser has its sidebar.
- **Width**: drag the edge between a sidebar and its window (200 to 440 pt): that window's sidebar, the others keep theirs. The pair keeps its outer edges (`EdgeDrag`, unit tested): the window is asked to make the room the pointer wants, by the same steps as a show (`WindowSteps`, its far edge kept), and the sidebar is as wide as the room the window has really made, read off the screen and followed every tick. At most one call is out to the browser: the pointer's latest width is what the next call asks, and it goes only once the window server shows the last one landed. On macOS 26 a drag is live; on macOS 27 the window trails by its animation and never cuts one short into a frame nobody asked for. A browser that has not answered yet has not given the space yet; one that stops short of a call is at its minimum (or, widening, as far as it goes from there), and nothing past that is asked again during that drag; the next drag or show asks again. A call that changes nothing is waited for three times the slowest landing of the drag so far (0.15 to 0.6 s), since the pointer's next width comes anyway. A step from VoiceOver or the keyboard (10 pt) has no button to come up, so it stays open until the window has answered, 0.3 s at most after the last step; steps taken meanwhile add up (`EdgeDrag.stepped`). While a browser has stopped answering, a drag or step asks its window for nothing and puts nothing back, since each call would wait a second: the width is taken from the window as last seen. When the button comes up, the window is waited for and checked (once more for its far edge, as a show is), its frame then is sent once more whole, each size held still 150 ms before it counts, so a call the drag stopped waiting for lands before it and a browser that widens itself back has done so (see Motion), its far edge checked once more after that, and the width saved is the room it made. Nothing is done at its next rest. A new window takes the width last dragged to. `betterlink sidebar settings set --width` sets every window's.
- **Keyboard** (`SidebarRows`, unit tested): Down from the New Tab field goes to the rows. Up and Down move, Left and Right close and open a folder (or move along the Favorites), Return opens, Delete closes the row's tab (a saved link with no tab is removed, a folder deleted), Escape goes back to the browser. What is typed in New Tab or a name never reaches the rows.
- **Show and hide**: Control-Option-S (change it under Sidebar › Show or hide), or Show/Hide Sidebar in the menu bar menu, for the browser window in front: hiding gives that window its space back, and the other windows keep their sidebars. With no browser in front the menu item is Show/Hide Sidebars, for every window, as is `betterlink sidebar settings set --shown`; new windows start that way too. `betterlink sidebar settings get` reports that (`shown`, and `width`): what a window gets when nothing was chosen for it, not what any one window shows. What was chosen for one window (hidden or shown, its width) holds while the window exists, across a betterlink relaunch too (`WindowMemory`, unit tested). The shortcut is registered only while an attached browser is in front.
- **Favorites and folders**, like Arc and Dia: each Sidebar Profile has a grid of Favorites and nested folders of saved links above the window's open tabs. Drag a tab onto the grid or a folder (or use its menu) to save it. Saved in sidebar.json in the settings folder.
- **A saved link keeps its tab** (`SidebarHolds.swift`, unit tested), like a pinned tab in Arc and Dia. Click a saved link and the tab it opens is that link's tab from then on, wherever you go inside the site: the tab stays on the link's row instead of dropping into the tab list, and the next click switches back to it instead of opening the site again. That is what makes a link to mail.google.com work, since the page moves on to its inbox address at once. When the tab is on another page than the saved one, the row shows "/ page title" after the name and a back arrow that returns the tab to the saved page; right-click has Back to Saved Page, Save This Page Here (the link now saves the page you are on), Close Tab and Copy Link. A tab that merely happens to be at a saved link's address also shows with the link, while it stays there. Saving a tab makes it the new link's tab. Held tabs come back to their links after the browser restarts: where each one was is kept in betterlink's own preferences on this Mac (never the synced settings folder), and the restored tabs are matched by address for the first minute. Closing a held tab yourself closes the link; quitting the browser doesn't. Tabs in private windows are never held or remembered.
- **A tab's right-click menu** has what the browser's own tab strip offers, because the sidebar stands in for it: Add to Favorites, Save to Folder, Copy Link, Reload, Duplicate, Mute or Unmute Tab, Move to New Window, Close Tab, Close Other Tabs, Close Tabs Below. A tab playing sound shows a speaker; click it to mute. Close Other Tabs and Close Tabs Below leave saved links' tabs alone.
- **Import** (Sidebar page › Import; `SidebarImport.swift`, unit tested): Import from Arc reads Arc's own sidebar file on this Mac (`~/Library/Application Support/Arc/StorableSidebar.json`) and makes a Sidebar Profile from each Space, with its Favorites, pinned tabs and folders; Today tabs are left out. Import Bookmarks reads a Chromium browser profile's `Bookmarks` file, or a bookmarks.html export from any browser, into one closed folder of the Sidebar Profile you pick. Only web addresses are taken, at most 5,000 links at a time, and nothing is fetched. Importing twice adds a second copy. The Arc reader was written from descriptions of the file's format and has not yet been checked against a real Arc install; if Arc's file doesn't fit, the import says so and changes nothing.
- **Folder icons** (`FolderIcon.swift`, unit tested): right-click a folder › Icon › Choose Emoji… opens a field in the row and a grid of common emoji below it: click one, or type or paste any other, and it is the folder's icon at once. (The Mac's own emoji picker opens only for the active app's text field, and the sidebar is a panel that never makes betterlink the active app, so it offers its own.) Choose Symbol… takes the name of a built-in symbol, as the SF Symbols app lists it (star.fill, folder.badge.person.crop); the row previews it as you type and Return sets it once this Mac draws it. Esc leaves the icon as it was, and Remove Icon brings the folder glyph back. The icon is drawn in place of the folder glyph, not beside it, so every row keeps one 16 pt icon column lined up with the saved links' site icons and the name doesn't shift; whether a folder is open still shows by its contents below it. A symbol this Mac doesn't draw (synced from a newer macOS) shows the glyph. Kept in sidebar.json as one string, `"icon": "emoji:📚"` or `"symbol:star.fill"`, left out when there is none, and synced with the folder (docs/sync.md). From the command line: `betterlink sidebar icon set <id> --emoji 📚` (or `--symbol star.fill`) and `betterlink sidebar icon clear <id>`; `sidebar list` shows each folder's `icon`.
- **Icons for saved links**: a link saved from a tab keeps that tab's icon. An imported link has none, so it shows the first letter of its name until its page has been open once; then it keeps the page's icon.
- **Drag and drop** (`SidebarProfile.place(_:at:)`, unit tested): drag favorites, saved links and folders to reorder them; drag any of them into or out of folders, at any depth, or between the Favorites grid and the folders (a link becomes a favorite and back). Drag a tab onto a spot to save it there. A line shows where it will land; dropping on a folder's middle puts it inside. A folder never goes into itself or the grid. Right-click: Move Up, Move Down, Move to…. Delete happens at once with Undo at the bottom for 6 seconds (a folder with things in it asks first); Undo puts back only what was deleted, where it was. A drop that wouldn't move anything (a folder into itself) shows no line and does nothing. During a drag the header line turns into the place for the first Favorite, and the New Tab line into the place for the end of the saved items, at the same height (`DropSwap`, unit tested): no row moves under the pointer (a test draws the whole sidebar with and without a drag and compares). A New Tab field that had the keyboard has it again when the drag ends, dropped or not (`DragFocus`, unit tested). A dragged row carries its key under betterlink's own type (`com.wkoutre.betterlink.sidebar-item`, exported in Info.plist), for betterlink alone (`SidebarDrag`, unit tested): dropped on a web page or another app it hands over nothing, where as text the browser opened it as an address. Not yet: selecting several rows, and moving rows from the keyboard.
- **Reordering tabs**: drag a tab in the sidebar's tab list before or after another to move it there in the browser's own tab order (the extension's `move`, 0.2.0). Only tabs of the same window, and pinned tabs only among pinned ones (the browser keeps them first); a drop next to itself does nothing.
- **Sidebar Profiles**: the ⚙ beside the Sidebar Profile's name at the top of the sidebar picks which Sidebar Profile the window's browser profile shows, makes a new one, renames or deletes this one (deleting asks first), and opens these settings (Sidebar Settings…). The + beside it makes a folder. A profile linked to nothing is shown for every browser profile not linked elsewhere.
- **Taking over the tabs** (on by default): when a Chromium window first has the focus with its browser in front, the browser's own tab strip is switched to vertical tabs and, where the browser can, collapsed (Chrome 158: View › Show Tabs Vertically, Collapse Vertical Tabs; Brave has the first), through the browser's menu with Accessibility: only those exact items of the View menu, never another menu (History, Bookmarks and Window items are titled by web pages), and only once the window is the browser's focused one. What state the tabs are in is read from the window itself, not from the menu (`TabStripReading`, unit tested with readings from Chrome and Brave): a tab strip above the toolbar is across the top, one beside or below it is a column, and a column about two tab heights wide is collapsed. An item is pressed only when the window is seen in the other state, the item is enabled and its checkmark doesn't say otherwise; a window that isn't collapsed yet and can't be pressed (its state can't be seen while it is still opening, or the menu still shows the window that had the focus before, or the browser has no Collapse) is looked at again, six looks in all over about two seconds (Chrome's menu was measured to catch up 78 to 947 ms after a window comes forward), and then left as it is (a window whose menu and tab strip still disagree then is looked at again the next time it comes forward), and a browser without the item is not read at all (Brave's item has no checkmark on or off, which used to switch its vertical tabs back and forth on every return to the window). After a press the window is looked at again, up to four times over about a second and a half (`TabStripTakeoverFlow`, unit tested): if it is seen still as it was, the item is pressed back and that browser's tabs are left alone until betterlink is next started; if it can't be seen, nothing more is pressed. At most two presses per window, and one run per window at a time. The sidebar sits beside the collapsed column, on either side, and never covers it (Nick: "it shouldn't overlap on top of (and effectively hide) the vertical tabs"). Each window is taken over once; switching apps and back does nothing again, except for a window left undecided, which is looked at again. Turning the setting off leaves the browser's tabs as they are (View › Show Tabs Vertically switches them back). On by default because Nick asked for the sidebar to take over tab management. No browser has an extension API to hide its tabs.
- **Motion**: every interaction in the sidebar animates briefly (ease-out, 0.12–0.18 s): folders open and close with their contents fading in, rows and favorites appear and disappear, hover and selection highlights fade, buttons dip when pressed, and the panel fades in and out. With Reduce Motion on (System Settings › Accessibility › Display), nothing animates. Showing and hiding slide the sidebar (`SidebarSlide`, unit tested): its outer edge stays put while its inner edge moves over 0.22 s, easing in and out, never past where the browser window really is, so the seam never opens. The browser moves with the slide as one motion, its far edge (away from the sidebar) where it was (Nick on 0.3.27: on show the browser's far edge animated in by the sidebar's width, then the whole browser slid; on hide the reverse). Two things make that work:

  - **Its enhanced user interface is off while betterlink moves it** (`EnhancedUI`, unit tested). With a browser app's `AXEnhancedUserInterface` on (an assistive app sets it, and on Nick's Mac something sets it for Chrome and Brave), macOS animates every Accessibility size and position set over about 250 ms, and a second set cuts the first short where it has got to; off, each set lands at once (measured with a probe on macOS 26.5.2 and 27.2.1, `betterlink-captures/probe27`). Right before the first set of a show, hide, new width, edge drag or quit, the browser's flag is read (one call, never cached); only when it is on is it set off, and read back, since the set's answer says nothing (Chromium on macOS 27 answers -25208, kAXErrorNotImplemented, and takes it). Right after the motion's final target lands (or it is capped, taken over, given up, or the window closes) it is set back to what it was and read back, once more if it didn't take. Never per frame, never for a motion that sends nothing, never when it was off, and only the browser whose window is moved; windows of one browser moving together share one hold. Before a flag is set off, the browser's pid, its process's start time (the kernel's) and the value are written to `enhanced-ui.json`, this Mac's alone (`~/Library/Application Support/betterlink/this-mac/`, never the settings folder, which may be synced), and removed once set back: a betterlink that stops in between sets it back at its next launch for each browser that is still the same process (same pid, same start time), and leaves a reused pid alone. Quitting holds and sets back each browser's flag within its 2.4 s, reading back only if time is left. Each read and set is timed in `trace.log` (`enhanced UI:` lines). With VoiceOver or Switch Control on (read at each motion), the flag is left alone: not read or set, and the browser moves as it did before (`EnhancedUI.assistive`).
  - **The browser is moved frame by frame with the slide** (`WindowGlide`, unit tested), while its sets land at once: each tick (120 a second) the frame for the slide's progress, in whole points. Narrowing, the size, the width it took read back at once (a browser at its minimum takes less), then the position that keeps its far edge at that width, both within one display refresh, which lands as one frame; widening, the same, size first where the window can grow in place, else the position first (a window can't grow past its screen's edge), then the size, then the position once more if it took less: there the far edge can be one step in (at most 16 pt) for one frame. The next frame only once the window server shows the last. A window whose sets haven't been seen to land at once has its first frame probe them: the size alone, at least 4 pt; shown within 50 ms, frames go out as pairs; not (animated anyway, late, busy, dropped), `WindowSteps` take over at once, as below. The glide gives way to them as well when a frame stops short or a size changes nothing, and stops at a change no call of the frame can make (someone else's). It doesn't run with Reduce Motion, while the flag couldn't be set off, or for a pair moved back on screen at closing.

  Every show and hide then ends with `WindowSteps` (unit tested), as it always did: one Accessibility call at a time, each waited for until the window server shows it done. Narrowing, the size goes first and the position only once the size has really changed; widening, the reverse. Where sets are animated (the flag stuck on), that is the whole motion: the browser goes there in two moves (its size, then its place) and the sidebar shows only as far as the browser has gone; on the left side no order of a size and a position keeps the far edge still under a system animation. An open without a slide (a new width, a window followed or back from full screen) is shown beside the frame the browser was asked for, and revealed the same way, only up to where the browser really is, until the browser has made room: a slow or unmoving browser never has the sidebar's list over its content (`SidebarGuardTests` checks after every press that the panel's body is never over the browser for longer than 0.5 s plus the modelled animation; at 6971efa a new width's open lay 281 pt over a late browser for over 0.9 s). Reduce Motion: the sidebar at once, the browser as fast as it goes. Whenever the sidebar is closed at once or let go (the end of a hide, a refusal, someone else's change, quitting, turning it off), the panel is ordered out before its mask is lifted for the next show, never after: the mask is committed at once, so lifted first it drew the whole panel over the browser until the order-out (Nick on 0.3.27; live on 3d5c1e4, a 312-column flash 220 ms after the slide had hidden the panel, for 70 ms). Every open masks the panel to the browser's real edge before moving it beside the frame asked. A press of the shortcut during a show or hide is taken as asked, the last press winning: mid-slide it turns back (a show turned back mid-hide opens in the frame the window was closing to), and while a refused show's window goes back it is held until the window is there. The press it overrides never has a call sent again: a call of its still on its way is waited for before the new press sends anything, but never sent once more, nor checked for stopping short. Held still partway, it has landed there, and the new press's next call cuts short what is left of it; not started yet, it is waited for up to the cap, since it may still land and the new press works its calls out from where the window is. Quitting and turning the sidebar off the same (the review of ce5bf39: a hide sent a show's narrowing again, and on macOS 27 the window narrowed further before the hide widened it). Each call has landed when the window server's frame has reached what it asked, or has changed at least once and then held still for 150 ms (a narrower size: both, since a browser can take it and then widen itself back to its minimum). Held still short of what it asked, the call is sent once more first, since macOS 27 can hold an animation partway (2056 to 1900 pt, still for 250 ms, then on to 1776, in the review of 596bc4e): if the window moves again it goes on, and if it stays still another 150 ms, plus the longest this show or hide's calls took to start, it has stopped there. A window that hasn't moved at all since the call hasn't started on it (on macOS 27 an animation can begin late; a browser can answer late): that is waited for, the call sent once more every 0.6 s (a call can be dropped), and only the cap ends the wait: a whole show or hide, every call of it included, is capped at 3 s (`WindowSteps.cap`). A change to the window that the call in flight can't make (a size keeps the window's top left; a move keeps its size and goes all the way across toward where it was sent) is someone else's, the person's or another app's: betterlink sends nothing more, and their frame stands. Only that one call is weighed, since every call before it has landed. A show not yet answered is given up then, the sidebar closed. Hiding, quitting, turning the sidebar off or setting a new width while an open (by the shortcut, when a window is first followed or back from full screen, or a new width's), a hide or a new width's close is still under way closes the pair in the frame it began in, never one worked out from where the browser has got to so far. Every show, hide, refusal and cap ends by sending betterlink's final target for the window once more, whole (its size and its place; one the window already looks done with is sent twice, since its landing can't be seen): Accessibility sets are done in order, so a call of betterlink's still on its way (one the cap cut off, a late browser's) lands before it, and the window ends there. That last call is betterlink's last word: whatever the window does after it is someone else's and stands, and a window at rest, open or closed, is never moved because it changed. Nothing is remembered of calls that may land late, and no change is ever matched against them. So a browser that answers too slowly for the cap gets its exact frame back, the sidebar closed, with the "didn't make room" note; pressing again tries again, and no width is lost. A tiling app that puts the window back once betterlink is done is another app's change, which stands. Giving space back, a size the window doesn't take leaves it where it was put rather than moving it back. A sidebar that comes or goes with its window (minimized, its browser hidden, back again) fades (`Fade`, on its own timer). Diagnostics: with `BETTERLINK_TRACE=1`, each window drag logs how far the sidebar trailed the window, and each show and hide (what the window was asked, and what the window server shows it got) and each drag of the sidebar's edge (the window before and after, the sidebar's width) is logged, as is the New Tab field's keyboard around each row drag, to `trace.log` in the settings folder.

- **Where the two meet** (`TabSyncCore/SidebarSeam.swift` and `WindowCorner.swift`, unit tested): the panel's top, bottom and seam are the window's edges, each on its own pixel of the screen it is on; it is never cut to the screen's visible frame, which would leave its top short of the window's. The panel reaches over the window's edge as far as the window's corner goes (31 pt for a 20 pt corner at 2x), in whole points, and is drawn there only in the two notches the window's rounded corners leave open; the rest of that strip is clear, so a press there is the window's. The sidebar's two outer corners are the window's own corner, so the pair's four corners match.
  - **The radius is the window's own.** The window server reports each window's corner radius (on macOS 26.5: Chrome and Brave 20, Dia 16, a window with a toolbar 26), and betterlink asks it when a window is first followed, when the window enters or leaves full screen, and each time the window comes to rest (150 ms after its last move with the mouse up; not while it is dragged or slid); never per frame or on a timer (one read took 0.04 to 0.2 ms here). The calls are private SkyLight ones, looked up by name and never linked (`WindowServer.cornerRadius` lists them and how they were checked), verified on macOS 26.5.2 only. **Fallback:** when betterlink can't read corner radii on this Mac at all (any other macOS major version, one of the calls missing, an Intel Mac, where they are not looked up, or the fallback forced), every sidebar is cut for 20 pt, Chrome's and Brave's radius; the Sidebar page says so and `betterlink sidebar settings get` shows `readsWindowCorners: false`. - **Which tabs** (`WindowPairing`, unit tested, and run against a model of late and missing words with the truth known): which of the browser's own windows each window is, is worked out again whenever anything new is known (the tab lists, a window's title or resting place, the focus, a window coming or going; a window's title while its browser is behind another app is read at the next pairing, not when it changes, so a window renamed then with no tab event is paired at the next tab list or window event), from three sources: Accessibility (each followed window's title and frame, and which has the focus), the extension (each browser window's active tab's title and frame, and which has the focus), and the window server (where every window of the browser is, on every Space, without titles). Accessibility lists only the windows on a Space that is showing, a profile without the extension or an Incognito window is in no session, and the sides' words arrive apart, so nothing is kept as settled; what is kept from the last look only bridges the moments they are out of step. (1) A browser window is beside at most one window. (2) A pairing is dropped, whatever made it, once title and frame both say otherwise. (3) The focus counts only once it has held: the same window and the same browser window focused at two looks 0.3 s apart (betterlink looks again then), and never against a title that says no. Then it decides, between look-alikes too, and what it paired stays through later look-alikes and app switches for as long as it looks right, or has not looked wrong (its title or frame saying no) for more than 3 s, which is longer than the browser's titles are ever behind. (4) A word on the focus that hasn't held changes nothing. Without the focus, a pairing needs a window and a browser window at the same place whose active tab's title the window title starts with, nothing else that is free matching as well, and every other window of the browser at that place accounted for: as many browser windows reported there as windows the window server shows there. One more window than that could be the one meant (a window on another Space has no title to go by), so the window shows nothing; a followed window whose title plainly says it is another takes no part in the count. Such a pairing is let go as soon as any of that stops being true. Windows that can't be told apart show nothing until the focus has held or a title or frame differs. (5) Being out of step blanks nothing: a pairing that title or frame still supports stays through moves, new titles and a stale word on the focus. While the focus is being given its 0.3 s the sidebar shows nothing rather than a reason; so it does while the focused window's title says it is another than the browser's focused one, for 3 s at most (betterlink looks again then), after which it says it can't see the window. The popups and app windows the extension reports are browser windows to the pairing like any other: each accounts for its own window where the windows at a place are counted (a palette lying exactly on a normal window, left out, would be one window too many there and blank that window's sidebar until it had the focus; `WindowWordTests`), and a window paired with one gets no sidebar (see Which windows). While a palette that isn't followed has the focus, no followed window is passed off as the focused one: the browser then says its popup has the focus, and the window that last had it could be paired with that popup. It never guesses: a click in the sidebar switches, closes and opens tabs, so the wrong window's tabs are worse than none. A window the extension doesn't report (an Incognito window without Allow in Incognito, or a browser profile without the extension) shows one line saying so instead of another window's tabs. The window server's list is read when a window is made, closed, comes to rest or takes the focus, when an app comes forward and when the extension reports one window more or fewer, never when tab lists or titles arrive and never on a timer; of it, only the browser's windows at the standard layer and at least 100 pt each way count (its helper windows there are menu-bar-high strips, bubbles and 1 and 64 pt squares).
- **Profiles**: each browser profile runs its own copy of the extension, so each is its own session. The extension keeps a random id in its own `chrome.storage.local` (the `storage` permission); betterlink finds that id in `<profile folder>/Local Extension Settings/<extension id>/` to learn which profile a session is, and reads the profile's name from the browser's `Local State`. A profile not found is looked for again every 5 s for its first minute (the browser writes the storage a moment after the extension starts), then every 30 s, so one not found within a minute shows up to 30 s late (it was 5 s). For the sidebar's color it also reads the profile's `Preferences` (a custom theme's color) and the frame color in `Local State`, again on the next tab change at least 30 s later, so a change in the browser shows up. It reads only those files, and only those fields; never page data.
- **Icons** come from the browser's own favicon cache through the extension (`favicon` permission), as data: URLs. betterlink itself fetches nothing.
- The panel is non-activating: clicking it never takes the browser out of the front. Checked live (at f18e95d) for a sidebar whose browser is not the front app: a click on a tab row switches to that tab and brings that browser and its window forward; the New Tab field takes the keyboard while the other app stays in front, and Return opens the tab and brings the browser forward; the right-click menu opens and stays open.

## Browser coverage

- Chromium family (Chrome, Brave, Edge, Arc, Vivaldi, Dia): this extension as is. Each browser keeps its own `NativeMessagingHosts` folder under the data folder betterlink already knows (`Browser.dataFolder`), except Brave, which reads Chrome's (`HostRegistration.readFolder`).
- Firefox: same design; it needs `browser_specific_settings`, a host manifest under `~/Library/Application Support/Mozilla/NativeMessagingHosts`, and `browser.*` (the events are the same).
- Safari: a Safari Web Extension inside the app bundle, talking to the app through `SFSafariApplication`/app groups instead of a stdio host. Same events, different transport.

## Known gaps (prototype)

- Events that fire while no app is connected are not queued; the snapshot on connect covers them.
- Incognito windows are only visible if the extension is allowed in incognito; the sidebar says it can't see one that isn't.
- A held tab is found again after a browser restart by its address. A tab the browser restores later than a minute after starting, or at another address, goes back to the tab list.
- Reopening a closed window (History › Recently Closed) brings its tabs back with new ids, so saved links there take their tabs back only where the address still matches.
- The extension is not in any store; it is loaded unpacked.
- In a browser that shows no tab group in any window (Dia), telling a palette from a browser window rests on the extension: without it installed and connected there, every standard window has a sidebar, a palette included (it shows the line about a window betterlink can't see). With it, a palette whose title or place doesn't match what the extension reports for it is not paired, gets no word, and has a sidebar after 0.6 s.
- A palette already open when betterlink starts, or when its browser's extension has not connected yet, gets a sidebar at once (nothing says a word will come) and loses it on the settled pass when the word comes. So does an app window of a browser started with only that window.
- In such a browser, a real browser window that one passing pairing calls a popup (the focus moving to a palette, say) is let go and has no sidebar until it is resized or comes back from the Dock, which has it judged afresh. A real palette resized there is followed again and let go again; if its word misses the 0.6 s wait it shows a sidebar for a moment, and with the extension not connected it keeps one until the extension connects.
- Without the extension connected, a browser of that kind in which one window shows a native tab view would count as one that shows its tabs, and its real windows would lose their sidebars after their looks. Not seen in any reading; with the extension connected the windows it calls normal keep theirs.
- Not read live: a window that is in native full screen with its toolbar hidden, or in the Dock, when betterlink starts. If such a window shows no tabs then, it has no sidebar until it leaves full screen (a resize) or comes back from the Dock.
- Not read live either: Chrome's Task Manager, which may show a tab group of its own, and whether Chrome sends tab events for the tabs of app windows.
- Which window is which is told from look, place, focus and a count of the browser's windows, so:
  - A window at the same place as another window of the browser that the browser doesn't report (an Incognito window, a profile without the extension), on any Space, shows nothing until it has had the focus for 0.3 s with its browser in front; unless that other window is on a showing Space and plainly on another page. So do windows at the same place on the same page.
  - A word of the browser's on the focus that comes more than 0.3 s late (its extension asleep, the browser busy) can give a look-alike another window's tabs. That lasts while the two look alike, and at most 3 s after a title or frame of theirs differs. `BETTERLINK_TRACE=1` logs both sides' words on the focus, so the gap can be measured.
  - A window whose title and place both change before the browser reports either shows nothing until it does.
  - The count is of the browser's windows as last read: a small window of the browser (a dialog, DevTools) dragged exactly onto a browser window is counted at the next window or app event, and one that closed counts until then, which blanks at most.
  - A helper window of a browser at the standard layer and exactly at a browser window's frame would keep that window's sidebar blank until it has the focus. None was found in Chrome or Dia.
- In Mission Control a sidebar shows as a window of its own beside its browser window.
- A window dragged to another Space in Mission Control leaves its sidebar behind until the next change of app, focus or Space; then it is taken away, and shown again where the window is.
